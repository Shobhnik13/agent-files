The big picture

 YOUR LAPTOP                    YOUR ISP / 1.1.1.1 / 8.8.8.8          THE INTERNET'S NAME SERVERS
 +----------------+             +-------------------------+
 | browser        |             | [2] RECURSIVE RESOLVER  | ---> root servers      (who runs .com?)
 |   |            |  question   |   cache                 | ---> .com servers      (who runs example.com?)
 | [1] STUB       | ----------> |   asks around for you   | ---> example.com's     (what is www?)
 |   RESOLVER     | <---------- |                         |      [3] AUTHORITATIVE
 +----------------+   answer    +-------------------------+          SERVERS
  • 1 lives on your machine and only asks one question.
  • 2 does the legwork: walks the chain of servers and remembers answers.
  • 3 are the owners of each part of the name. They hold the real answers.
Analogy: you ask the hotel front desk (stub) for a restaurant's phone number. The concierge (recursive resolver) calls the city directory, then the district office, then the restaurant itself (authoritative), and writes the number in a notebook so the next guest gets it instantly.

1. Stub resolver

What problem it solves

  • Every program needs names turned into addresses. None of them should have to know how DNS works.
  • The stub is a small part of the operating system that takes the question and hands it to one configured server.

Flow

 browser: "www.example.com?"
    |
    v
 [1] HOSTS FILE      local overrides, checked first
    |  not found
    v
 [2] LOCAL CACHE     answers seen recently on this machine
    |  not found
    v
 [3] ASK ONE SERVER  the configured recursive resolver
    |
    v
 answer: an address, or "no such name"

Steps in plain words

  • Hosts file: a plain text list on the machine. If the name is there, DNS is never asked.
  • Cache: recent answers are kept for as long as each answer says it may be kept.
  • One question out: the stub does not walk the chain itself. It asks for a full answer and waits.

2. Recursive resolver

What problem it solves

  • No single server knows every name. The answer is spread over many owners.
  • The recursive resolver finds the right owner by asking from the top down, then hands back one final answer.

Flow

 question: www.example.com
    |
    v
 [1] CACHE?                       have it and not expired -> answer now
    |  no
    v
 [2] ASK A ROOT SERVER            "I don't know www.example.com,
    |                              but .com is run by these servers"
    v
 [3] ASK A .com SERVER            "example.com is run by these servers"
    |
    v
 [4] ASK example.com's SERVER     "www.example.com = this address"
    |
    v
 [5] STORE IN CACHE (for TTL seconds) -> answer the stub

Steps in plain words

  • Start at the top: the resolver ships with the addresses of the root servers built in.
  • Each answer is a referral: "not me, ask them". The resolver follows referrals until it reaches the owner.
  • Final answer: the owner's server answers with the record itself.

Caching

What is cachedFor how longEffect
Final answersThe record's TTL, set by the ownerRepeat questions answered instantly
Referrals (who runs .com)Their own TTLMost lookups skip the root entirely
"No such name"A time the owner setsTypos don't hammer the servers
The trade-off: a long TTL means fast answers but slow changes. If the owner changes an address, old answers live on in caches until they expire.

3. Authoritative servers

What problem it solves

  • Someone has to be the source of truth for each name.
  • Each owner runs (or rents) servers that answer only for their own part of the tree.

The tree of names

                    . (root)
                    |
      +-------------+-------------+
      |             |             |
     com           org           net        <- top-level domains
      |
   example                                  <- owned by someone
      |
   +--+--+
   |     |
  www   mail                                <- records inside example.com
  • A name is read right to left: root, then com, then example, then www.
  • Each level only knows who runs the level below it. That handing-down is called delegation.

Record types

TypeHoldsExample
AAn IPv4 addresswww -> 192.0.2.10
AAAAAn IPv6 addresswww -> 2001:db8::10
CNAME"This name is another name"shop -> www.example.com
MXWhich server takes mailexample.com -> mail.example.com
NSWhich servers own a zoneexample.com -> ns1.example.net

How it all connects

 app asks stub [1]
   -> stub asks recursive resolver [2]
        -> cache hit? answer
        -> else root -> TLD -> owner [3], following referrals
        -> cache the answer for its TTL
   -> stub caches it too, hands it to the app
   -> app connects to the address
